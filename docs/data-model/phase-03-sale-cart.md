## 1. Prisma schema

```prisma
enum SaleStatus {
  draft
  paid
  voided
  partially_refunded
  refunded
}

model Sale {
  id                 String     @id @default(uuid()) @db.Uuid
  store_id           String     @db.Uuid
  staff_id           String     @db.Uuid
  shift_id           String?    @db.Uuid
  status             SaleStatus @default(draft)
  subtotal           Int        // minor units, before discounts
  discount_total     Int        @default(0)
  tax_total          Int        @default(0)
  total              Int
  client_ref         String
  note               String?
  created_at         DateTime   @default(now())
  updated_at         DateTime   @updatedAt
  paid_at            DateTime?
  voided_at          DateTime?
  voided_by_staff_id String?    @db.Uuid
  void_reason        String?

  store              Store      @relation(fields: [store_id], references: [id])
  staff              Staff      @relation("SaleStaff", fields: [staff_id], references: [id])
  shift              Shift?     @relation(fields: [shift_id], references: [id])
  voided_by          Staff?     @relation("SaleVoidedBy", fields: [voided_by_staff_id], references: [id])
  sale_items         SaleItem[]
  stock_movements    StockMovement[]

  @@unique([store_id, client_ref])
  @@index([store_id, status, created_at])
  @@index([store_id, paid_at])
  @@index([store_id, staff_id, created_at])
  @@index([shift_id])
}

model SaleItem {
  id                            String   @id @default(uuid()) @db.Uuid
  sale_id                       String   @db.Uuid
  item_id                       String   @db.Uuid
  item_name_at_sale             String
  sku_at_sale                   String
  quantity                      Int
  unit_price_at_sale            Int
  discount_amount               Int      @default(0)
  discount_reason               String?
  discount_approved_by_staff_id String?  @db.Uuid
  line_total                    Int

  created_at                    DateTime @default(now())
  updated_at                    DateTime @updatedAt

  sale                          Sale     @relation(fields: [sale_id], references: [id])
  item                          Item     @relation(fields: [item_id], references: [id])
  discount_approved_by          Staff?   @relation("SaleItemDiscountApprovedBy", fields: [discount_approved_by_staff_id], references: [id])

  @@unique([sale_id, item_id]) // one line per item per sale; merge quantities
  @@index([item_id])
}
```

## 2. Field rules

**Sale**
- `client_ref` is generated by the client and unique per store. Creating a sale with an existing `client_ref` returns the existing sale (idempotent) rather than failing or duplicating (ADR 0006).
- `staff_id` is the author (taken from auth, never from input). `shift_id` is set from the author's open shift at creation; if none is open, follow ADR 0010 (reject or leave null).
- All money is integer minor units, **computed on the server**. Clients never send totals.
- Totals convention (confirm with ADR 0008):
  - `subtotal = Σ (quantity × unit_price_at_sale)` before discounts
  - `discount_total = Σ line discount_amount`
  - `total = subtotal − discount_total + tax_total`
- The build plan models discounts only at line level. A sale-level discount must be allocated across lines.
- `tax_total` is `0` until tax rules exist (ADR 0008). Per-line tax is a later additive column.
- Status transitions in v1: `draft → paid` (Phases 4–5), `paid → partially_refunded → refunded` (Phase 7). All enum values exist now so later phases need no enum migration, but Phase 3 code only creates and edits `draft`.
- Only `draft` sales are editable. Once `paid`, a sale and its lines are immutable.

**SaleItem**
- Snapshot fields (`item_name_at_sale`, `sku_at_sale`, `unit_price_at_sale`) are copied from `Item` when the line is added and **never** updated afterwards, even if the draft is long-lived. Adding the same item again merges quantity into the existing line.
- `line_total = quantity × unit_price_at_sale − discount_amount`.
- A discount requires `discount_reason`. Discounts above the ADR 0008 threshold require `discount_approved_by_staff_id` pointing to an active `manager`/`admin` of the same store.
- Only `active` items can be added to a cart. Quantities are integers (see Phase 2 note on fractional units).

## 3. DB constraints and raw SQL

```sql
ALTER TABLE "Sale" ADD CONSTRAINT "Sale_amounts_nonneg"
  CHECK ("subtotal" >= 0 AND "discount_total" >= 0 AND "tax_total" >= 0 AND "total" >= 0);
ALTER TABLE "Sale" ADD CONSTRAINT "Sale_total_formula"
  CHECK ("total" = "subtotal" - "discount_total" + "tax_total");
ALTER TABLE "Sale" ADD CONSTRAINT "Sale_paid_has_timestamp"
  CHECK ("status" NOT IN ('paid','partially_refunded','refunded') OR "paid_at" IS NOT NULL);
ALTER TABLE "Sale" ADD CONSTRAINT "Sale_void_fields"
  CHECK ("status" <> 'voided' OR ("voided_at" IS NOT NULL AND "voided_by_staff_id" IS NOT NULL AND "void_reason" IS NOT NULL));

ALTER TABLE "SaleItem" ADD CONSTRAINT "SaleItem_quantity_positive" CHECK ("quantity" > 0);
ALTER TABLE "SaleItem" ADD CONSTRAINT "SaleItem_discount_bounds"
  CHECK ("discount_amount" >= 0 AND "discount_amount" <= "quantity"::bigint * "unit_price_at_sale");
ALTER TABLE "SaleItem" ADD CONSTRAINT "SaleItem_line_total_formula"
  CHECK ("line_total" = "quantity"::bigint * "unit_price_at_sale" - "discount_amount");
ALTER TABLE "SaleItem" ADD CONSTRAINT "SaleItem_discount_needs_reason"
  CHECK ("discount_amount" = 0 OR "discount_reason" IS NOT NULL);
```

Cast to `bigint` before multiplying so the checks cannot overflow `int4`.

## 4. Service-layer rules

- Every cart mutation (add/remove/change quantity/apply discount) recalculates and persists `subtotal`, `discount_total`, `total` in the same transaction as the line change.
- Authorization: a draft is editable by its author; managers/admins may edit others' drafts (confirm per ADR 0004/0010). Always filter by `store_id` from auth.
- **Stock is not touched while a sale is draft** and not reserved. Availability is validated at finalization.
- Shared finalize routine (implemented here, invoked by Phases 4–5), inside the caller's transaction:
  1. Lock the sale row (`SELECT ... FOR UPDATE`) and confirm status is `draft`.
  2. For each line, in ascending `item_id` order (avoids deadlocks), insert a `sale` `StockMovement` (`quantity_change = −quantity`, `sale_id` set) and atomically decrement `Item.stock_quantity` with a non-negative guard.
  3. Set `status = paid`, `paid_at = now()`.
  4. Write the audit row.
  Failure at any step rolls back everything.
- Voiding is **not defined by the build plan**. Recommended default until an ADR says otherwise: voids apply to drafts only (cancelling a cart); reversing a paid sale goes through the Phase 7 refund flow. If paid-sale voids are allowed, the ADR must define the stock reversal reason and cash treatment before implementation.

Audit actions introduced: `sale.created`, `sale.item_added`, `sale.item_removed`, `sale.item_updated`, `sale.discount_applied` (with approver), `sale.voided`.

## 5. Acceptance checklist

- [ ] Re-sending the same `client_ref` returns the same sale and creates no duplicate.
- [ ] Changing an item's name/SKU/price after adding it to a draft does not change the line.
- [ ] Totals always satisfy the DB formulas; client-supplied totals are ignored.
- [ ] A paid or voided sale rejects line edits.
- [ ] Stock is unchanged after cart operations; only finalization writes movements.
- [ ] Cross-store sale and item ids behave as not found.
- [ ] No `Payment`, `Receipt` or `Refund` model was added.
